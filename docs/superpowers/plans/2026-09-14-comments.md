# Comment Notification Implementation Plan

**Goal:** Add authenticated `POST /api/v1/comments` and create a notification for the product seller.

**Architecture:** Follow the existing controller/service/repository structure. Products are the existing owned content; accept `productId` and the example's `postId` alias. Resolve the author from the authenticated email and the receiver from `Product.seller`. Persist comment and notification in one transaction, and publish only after commit.

**Tech stack:** Existing Spring MVC, Security, JPA, Flyway, PostgreSQL, JUnit and Mockito dependencies.

**Source requirements:** User-provided CommentService example and repeated request for `POST /api/v1/comments`.

A standalone H2 check in PostgreSQL compatibility mode reproduced the author-deletion foreign-key failure before adding `ON DELETE CASCADE`, then verified the migration SQL, deletion behavior and SQL rollback. These checks do not replace live PostgreSQL or browser WebSocket verification.

## API contract

Request: `{"productId":85,"content":"Is this available in blue?"}` with the normal Bearer token. `postId` also identifies a product. Return HTTP 201 with the existing ApiResponse envelope and a payload containing id, productId, authorId, content and createdAt. Content is required and limited to 2000 characters; productId is a positive required integer. Missing/deleted products return 404. Authentication follows the existing security configuration.

The notification uses the seller's id and email, `COMMENT_ADDED`, title `New Comment`, a product-specific message, saved comment id and reference type `COMMENT`. No separate post domain or comment management endpoints are added.
